# Design: federated-kg

## Context

Per-project KGs are bounded (MAX_ENTITIES = 200, MAX_EVENTS = 150 per
project) and fully derived — `knowledge_model.rs` rebuilds them from
files. So a 7-member workspace federates at most ~1,400 local
entities: small enough for in-memory resolution, no clever indexing
needed. The per-project DB is the member's source of truth here; the
workspace KG is a **derivation of derivations** and must stay
disposable. `workspace.rs` (feature 2) provides member enumeration and
handles; `.ken-workspace/` is the established home for workspace-level
derived data.

## Goals / Non-Goals

- Goals: one queryable graph over all members; Karpathy principles
  concretely — every node addressable (`kg://`), summarized, densely
  linked both directions, and the whole graph rebuildable from
  members; cheap incremental refresh; merge quality that degrades
  safely (unmerged duplicates are ugly, wrong merges are lies —
  prefer ugly).
- Non-Goals: editing the KG by hand (it's derived; corrections belong
  in member content); federating events in v1 (entities + edges +
  pointers only; events stay per-project); real-time sync (debounced
  rebuild is enough); embeddings in kg.sqlite (semantic search stays
  per-project; `kg-routing` composes the two).

## Decisions

### D1. Separate kg.sqlite, not tables in member DBs

Member DBs stay single-project-pure (schema v12 is already landing in
`semantic-index`; no workspace coupling there). kg.sqlite has its own
tiny schema version and lives beside workspace.json — derived data in
the workspace's own home, deletable without touching any member.
Rejected: a "primary member" hosting global tables — breaks when that
member is removed, and muddies "per-project DB is per-project".

### D2. Resolution: deterministic first, LLM only for near-misses

Tier 1 (normalized name + kind equality) is pure, testable, and
handles the dominant case (the same project name, person, or tool
mentioned across repos). Tier 2 exists because "SR" vs
"ShatteredRealms" is real: candidate pairs are generated by cheap
signals (shared token, edit distance ≤ 2 on normalized names, one
name contained in the other), batched to the local model
(Background), capped at 100 pairs/build with a per-pair yes/no + merged
canonical name contract. Any parse failure, timeout, or hedged answer
⇒ no merge. A wrong merge poisons every downstream link, so the bias
is maximally conservative; duplicate nodes merely look redundant and
still work.

### D3. Build is snapshot → merge, cached per member

Phase 1 reads each member DB into a `MemberSnapshot` (entities, edges,
entity→source-file map) and caches it in kg.sqlite keyed by the
member's `knowledge_model_built_at` watermark. Phase 2 merges all
current snapshots into the global tables (full re-merge each time —
at ≤1,400 entities this is milliseconds, and it sidesteps incremental
merge-state bugs entirely). Incrementality is therefore only "skip
re-reading unchanged members", which is the expensive part. Rebuild
runs one-at-a-time with a cancel token, mirroring the ingest engine's
discipline.

### D4. Addressing and back-links are first-class

`kg://<global-entity-id>` and `ken://<project-id>/<rel-path>` (schemes
fixed in README.md) are the only currencies the UI and `kg-routing`
use. Back-links are not stored separately — `global_edges` is queried
in both directions and `doc_pointers` gives entity→file; file→entity
comes from the member's own tables via `entity_links`. Wiki-page reads
(`workspace_kg_entity`) assemble all of it in one command so the
frontend never joins.

### D5. LLM passes are optional garnish, never load-bearing

Summary merge, near-miss adjudication, and the typed-relation linking
pass all have non-LLM fallbacks (longest summary, no merge, cooccur
edges with `relation: "related"`). A build with the model unavailable
completes and is marked `llm_passes: false` in meta; the next build
with a model available upgrades it. This keeps workspace-KG builds
possible immediately after workspace creation, before any model
download.

### D6. Map view reuses, not forks

The existing map component gets a data-source seam: per-project mode
feeds it local entities (unchanged), workspace mode feeds global
entities + a `color_key` (member hue; merged nodes get a multi-member
badge). Interaction differences (click → wiki panel, pointer click →
focus switch + open) live in the workspace wrapper, not the shared
component.

## Risks / Trade-offs

- **Bad merges** — mitigated by D2's conservatism; a "Split" action is
  deliberately out of scope (the KG is derived; if a merge is wrong,
  the adjudication prompt/rules need fixing, and `entity_links` makes
  wrong merges inspectable).
- **Build storms** when several members finish knowledge models
  together — single debounced trigger (30 s) + one-build-at-a-time +
  snapshot cache makes the worst case one cheap re-merge.
- **Members opened outside the workspace** drift their KGs — the
  watermark check catches it on next workspace open; a stale badge in
  the Map view shows members whose snapshot is behind.
- **Scale** beyond ~15 members — full re-merge stays fine (≤3k
  entities); LLM pass caps are per-build so quality catches up over
  successive builds.

## Migration

None for members. kg.sqlite is created on first build (flag on +
workspace open), versioned independently, and safe to delete at any
time.
